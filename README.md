### Описание основных преимуществ методов масштабирования

**1. Активный master-сервер + пассивный репликационный slave-сервер**  
Классическая схема Master-Slave.  
**Преимущества:**
- Простота настройки и эксплуатации.
- Хорошее масштабирование операций чтения (SELECT-запросы можно отправлять на Slave).
- Slave можно использовать для аналитики, отчётов и резервного копирования.
- Минимальный риск конфликтов данных.

**2. Master-сервер + несколько slave-серверов**  
**Преимущества:**
- Значительное горизонтальное масштабирование чтения.
- Высокая доступность чтения (при выходе из строя одного Slave остальные продолжают работать).
- Возможность географического распределения Slave-серверов.
- Master занимается только записью, что повышает общую производительность системы.

**3. Distributed Replicated Block Device (DRBD)**  
Блочная репликация на уровне ядра Linux.  
**Преимущества:**
- Высокая надёжность и целостность данных.
- Быстрый failover (переключение на резервный сервер).
- Работает на уровне дисков, поэтому подходит для любой СУБД.
- Возможность работы в синхронном режиме (нулевая потеря данных).

**4. SAN-кластер (Storage Area Network)**  
Использование общего сетевого хранилища.  
**Преимущества:**
- Все серверы работают с одним общим хранилищем (репликация не нужна).
- Высокая производительность дисковой подсистемы.
- Упрощённый и быстрый failover.
- Удобное централизованное управление данными и бэкапами.

# Репликация и масштабирование
# Задание 1
## 1. Репликация Master-Slave
Это самая распространённая схема репликации.

Master (ведущий) — основной сервер, на котором происходят все операции записи (INSERT, UPDATE, DELETE).
Slave (ведомый) — один или несколько подчинённых серверов, которые получают изменения от Master и обслуживают запросы на чтение (SELECT).

Как работает:

Master записывает все изменения в binary log.
Slave копирует этот журнал к себе в relay log.
Slave применяет изменения на своих данных.

Плюсы:

Хорошо масштабирует чтение (можно добавить много Slave).
Простая настройка.
Нет конфликтов данных.

Минусы:

Master — единая точка отказа для записи.
При падении Master нужно вручную или автоматически повышать Slave в новый Master.

Типы репликации: покомандная (SQL-запросы) и построчная (ROW).

## 2. Репликация Master-Master
В этой схеме все серверы равноправны — каждый сервер одновременно является и Master, и Slave.

Запись можно выполнять на любой сервер.
Изменения автоматически распространяются на все остальные серверы.

Плюсы:

Высокая отказоустойчивость — если один сервер упал, запись продолжается на остальных.
Лучшая доступность для операций записи.

Минусы:

Более сложная настройка.
Возможны конфликты при одновременной записи одной и той же записи на разных серверах.
Требует дополнительных механизмов (например, разные server-id, auto-increment offset и т.д.).

# Задание 1. СУБД
### 1.1
Для бюджетирования проектов, формирования финансовых отчётов и прогнозирования рисков лучше всего подойдёт реляционная СУБД — PostgreSQL.

Развёрнутое пояснение:
Эта система требует строгой структуры данных, точных расчётов и гарантии того, что данные не будут потеряны или повреждены. Реляционные базы данных обеспечивают это благодаря ACID-транзакциям, constraints (ограничениям), foreign keys и возможности писать сложные аналитические запросы. Это критично для финансовой отчётности.

### 1.2
Для лендингов — NoSQL (например, MongoDB).
Для CRM — реляционная СУБД PostgreSQL.

Пояснение:
Лендинги получают много неструктурированных данных от посетителей и должны быстро записывать лиды. NoSQL базы в этом случае быстрее и гибче. В CRM же важны связи между клиентами, сделками, менеджерами и историей — здесь лучше работает реляционная модель.

### 1.3
Для хранения корпоративных норм, правил и обучающих материалов лучше всего подойдёт PostgreSQL.

Пояснение:
Информация имеет чёткую структуру (разделы, подразделы, документы, доступ по ролям), поэтому простая и понятная реляционная структура будет наиболее удобной.

### 1.4
Для задач логистики (построение маршрутов доставки и распределение курьеров) лучше всего подойдёт графовая СУБД (Neo4j).

Пояснение:
В логистике очень много связей (объект — материалы — курьеры — маршруты). Графовые базы специально созданы для работы с такими сложными связями и позволяют быстро находить оптимальные пути.

### 1.5
Да, все перечисленные задачи можно решить с помощью одной СУБД — PostgreSQL.

Пояснение:
PostgreSQL сочетает в себе возможности реляционной и документной (NoSQL) базы благодаря типу JSONB. Также есть расширения (PostGIS для геоданных, Citus для масштабирования), что позволяет закрыть почти все сценарии в одной системе.

# Задание 2. Транзакции
### 2.1
Пошагово процесс пополнения баланса телефона через систему оператора сотовой связи:

Пользователь в личном кабинете или приложении оператора выбирает сумму пополнения и подтверждает платёж.

Система оператора создаёт запись о транзакции в своей базе данных со статусом pending.

Система оператора отправляет запрос в банк (или платёжный шлюз) на списание средств с карты клиента.

Банк выполняет свою транзакцию и возвращает ответ оператору (успешно / отказ).

При получении положительного ответа система оператора увеличивает баланс телефона в своей БД и меняет статус транзакции на success.

Пользователю отправляется уведомление об успешном пополнении.

Если банк вернул отказ — транзакция в БД оператора переводится в статус failed, баланс не изменяется.


# Задание 3. SQL vs NoSQL
### 3.1
Пять преимуществ SQL-систем по отношению к NoSQL:

ACID-транзакции — гарантируют, что данные либо полностью обновятся, либо останутся без изменений (очень важно для финансов и учёта).

Сильная схема данных — заранее определены таблицы, типы полей и связи, что снижает количество ошибок.

Мощный язык SQL — позволяет писать сложные запросы с JOIN, подзапросами и аналитическими функциями.

Отличная поддержка аналитики — легко строить отчёты и работать с BI-инструментами.

Высокая целостность и безопасность данных — встроенные механизмы защиты и контроля доступа.
